# 分析报告输出格式

本文件定义复杂场景的完整分析报告结构。简单或局部问题不要套用完整模板，只输出「结论」加最小结构建议。

只有确认存在多个独立决策点或多维组合时，才按 A / B / C 三段输出；没有内容的章节直接省略。

---

## 输出总原则（可读性）

1. **结论先行**：先写 A 段，读者只读 A 段也能拿到答案；B 段是为这些结论提供推理依据。
2. **维度分析用「原始 → 问题 → 目标」三段式**：不要只丢一行表格结论，要让读者看到推理链。
3. **表格只用于天然是矩阵的信息**（维度取值、维度角色、非正交判定、决策表）；判断理由一律用文字。
4. **代码只给关键接口、分发点和结构体字段**，并标注「示意，按需调整」；不要铺空实现。
5. **术语首次出现给一句定义**，之后不再重复解释；名词细节指向对应 reference。
6. **不使用「改造前 / 改造后」**：代码可能尚未存在，统一用「原始字段 / 业务描述 → 目标维度与结构」。
7. **篇幅自适应**：简单场景只输出 A + B2/B3 + 最小结构，不要为了凑模板写空章节。

---

## A. 结论

### A1 一句话结论

用 1~3 句说清：这段业务最核心的建模问题是什么、维度应该怎么拆、最终用什么结构承载。

示例：

> 该需求的核心问题是 `ProductType` 一个字段同时承载商品形态、销售模式、贸易模式三层含义，导致每个决策点都在解析同一个字段。应先把它拆成四个独立事实维度；税费决策点在它们之上再派生 `TaxModel` 中间模型，用决策表选模型、策略算金额。

### A2 结论速览

用一张紧凑表把「问题 → 结论」一次列清：

| 问题 | 结论 |
|---|---|
| `ProductType` 语义混杂 | 拆成 ProductForm / SaleMode / TradeMode / FulfillmentMode |
| 税费受地区、税类、主体共同影响 | 派生 TaxModel，用决策表选择 |
| 中国香港 + 任意商品 | 免税，属规则而非策略 |
| 税率随地区 / 税类变化 | Config Matrix，不建策略 |

## B. 分析过程

### B1 业务与决策点

**推导方法**：不要凭空枚举决策点。先按业务自身的流程写出时间轴（不预设阶段，取自当前业务），再沿时间轴在每个时间点固定问四句：

```text
能不能？   ← 准入、资格、支持性判断     -> 通常落成 Rule / Policy
多少？     ← 金额、比例、数量、积分     -> 通常落成 Config / Matrix / Pipeline
哪个？     ← 选模型、选实现、选路线     -> 通常落成 Resolver / Decision Table
怎么变？   ← 状态流转、阶段推进         -> 通常落成 State Machine
```

**硬约束**：每个决策点必须填满三格（决策问题｜输入事实｜决策输出），缺一格即视为分析未完成。整张表按流程时间轴排序，第一列标出所在时间点，让决策点的先后顺序一目了然；同一时间点有多个决策点时重复该列即可。

| 流程时间点 | 决策问题 | 输入事实 | 决策输出 |
|---|---|---|---|
| 下单 | 优惠是否可用？ | 会员等级、地区、活动类型 | allow / deny + 原因 |
| 计价 | 税费怎么算？ | 地区、商品税类、主体类型、金额 | 金额 + 命中的税务模型 |
| 支付 | 支付方式是否可用？ | 渠道、支付方式 | allow / deny + 原因 |
| 履约 | 订单状态如何流转？ | 当前状态、事件 | 新状态 |

三格填写要求：

- **决策问题**：动词句式的明确问题（「是否可用」「怎么算」「选哪个」「怎么流转」）。
- **输入事实**：参与该决策的事实维度。
- **决策输出**：必须是具体形态——allow/deny + 原因、金额、选中的模型 / 实现、新状态。

**粒度过粗识别规则**：若一个决策点的「输入事实」横跨不相关领域，或「决策输出」混了 allow/deny 与金额等不同类型，说明它太粗，应拆成多个决策点后各自填满三格。

### B2 事实维度识别

先筛选，再分析。只把影响决策和变化的字段列为事实维度；只被读取、透传或展示的字段（如歌词、开播时间）是普通数据字段，要明确写出来排除，不进入后续分析。

格式：

| 维度 | 含义 | 可能取值 |
|---|---|---|
| 地区 | 交易发生地 | 大陆 / 香港 / 欧盟 / 美国 |
| 商品税类 | 税务口径下的商品分类 | 普通商品 / 图书 / 数字服务 |

被排除的普通数据字段：`orderId`、`createdAt`、`lyrics`（只展示，不参与决策）。

### B3 维度健康度分析（核心）

对每个有问题的维度，按统一三段式写推理段：

```text
原始：<业务描述或字段 / 枚举长什么样>
问题：<太粗 / 语义混杂 / 层级平铺 / 强耦合 / Context 过大>
目标：<拆成哪些事实维度 / 派生什么中间模型 / 建什么层级；每个维度的取值与来源>
```

按四类问题分小节，没有该类问题就省略。

#### B3.1 语义混杂或太粗 → 拆细

判断信号：一个字段被大量 if/else 解析；枚举值名字越来越长；同时影响多个不相关决策点；既表达类型又表达状态和来源；新增业务时总在追加复杂组合值。

原始：`ProductType` 是长枚举，如 `NORMAL_PHYSICAL_DOMESTIC`、`VIRTUAL_OVERSEAS`。

问题：一个字段同时表达商品形态、销售模式、贸易模式、履约模式四层含义，每个决策点都在解析它。

目标：拆成 `ProductForm` / `SaleMode` / `TradeMode` / `FulfillmentMode` 四个独立事实维度，各自参与不同决策点。

#### B3.2 强耦合 → 派生中间模型

判断信号：两个维度几乎总是同时出现；取值互相依赖；单独看都不表达完整业务语义；大量规则是同一组固定组合。

原始：业务里到处出现 `SaleMode == PRESALE && PaymentStage == DEPOSIT` 这类固定组合判断。

问题：两个维度单独看都不表达完整业务语义，组合后才稳定。

目标：保留原始事实，派生 `PurchasePhase` 中间模型，由 Resolver 统一推导，后续逻辑基于中间模型。

#### B3.3 层级平铺 → 分层

判断信号：枚举值有大量前缀重复；有明显父子分类；上层决定大流程、下层决定细节。

原始：`ProductCategory` 平铺成 `PHYSICAL_BOOK`、`PHYSICAL_FOOD`、`VIRTUAL_COUPON` 等。

问题：前缀重复，实际存在一级 / 二级分类，平铺会导致枚举爆炸和策略选择困难。

目标：上层 `ProductForm` 决定大流程分发，下层 `ProductCategory` 决定细规则与参数。

#### B3.4 Context 过大 → 按决策点拆

判断信号：一个 Context 装了用户、商品、支付、履约全部字段；策略能访问无关字段；测试数据难构造。

原始：一个 `OrderContext` 同时容纳用户、商品、支付、履约、金额等字段。

问题：决策点边界不清，每个策略都能访问过多字段，形成隐式耦合。

目标：按决策点拆成 `PriceContext` / `TaxContext` / `PaymentContext` / `FulfillmentContext`，每个只放该决策点需要的事实快照。

### B4 维度角色

先说明核心判断：同一个维度在不同决策点可以扮演不同角色。逐个决策点判断该维度是 Context 字段、Config 索引、Rule 条件，还是策略分发条件。

| 决策点 | 维度 | 角色 | 说明 |
|---|---|---|---|
| 价格计算 | 会员等级 | Config | 查折扣率 |
| 优惠资格 | 会员等级 | Rule | 判断等级是否足够 |
| 权益发放 | 会员等级 | Strategy 分发 | 不同等级流程不同 |

**规则识别**：只列需要跨 Policy 复用、独立配置或独立编排的 Rule；Policy 内部的简单判断不逐条建类型。

| 规则 | 条件 | 结果 | 放置位置 |
|---|---|---|---|
| 中国香港免税 | 地区 = 香港 | 走免税，不征税 | 收进 TaxEligibilityPolicy |

**Policy 识别**：列出规则较多、值得单独说明的决策点；简单场景可省略。

**参数识别**：列出哪些逻辑只是「值不同」。

| 参数 | 索引维度 | 示例值 | 建模方式 |
|---|---|---|---|
| 税率 | 地区 × 商品税类 | 大陆 / 普通商品 = 0.13 | Config Matrix |

**策略识别**：列出哪些逻辑是真正的「怎么做」。

| 策略接口 | 分发依据 | 策略实现 | 原因 |
|---|---|---|---|
| TaxStrategy | TaxModel | EUVAT / USSalesTax / MainlandIncludedTax | 算法不同 |

对包含多个方法的 Strategy，检查：是否表达同一业务能力？是否因同一原因变化？是否处于同一生命周期？是否所有实现都必须提供全部方法？是否混入了其他决策点？

### B5 非正交维度处理（核心）

先判定关系本质，再给处理方式，不要急着把组合做成策略。

| 非正交关系 | 类型 | 推荐处理 |
|---|---|---|
| 海外 × 赠品 | 非法组合 | Rule |
| 地区 × 商品税类 → 税率 | 同公式不同参数 | Config Matrix |
| 基础税 + 地区附加税 + 商品特殊税 | 多因素叠加 | Pipeline |
| 地区 × 商品税类 × 主体 × 发票 → 算法 | 互斥算法 | Decision Table + Strategy |
| 地区 × 商品税类 × 主体 → 税务口径 | 稳定业务概念 | Intermediate Model + Resolver |

若需要中间业务模型，给出「是否需要 / 原因 / 建议模型」，并可附决策表：

| 优先级 | 地区 | 商品税类 | 主体 | 税务模型 |
|---|---|---|---|---|
| 100 | 任意 | 免税商品 | 任意 | TAX_FREE |
| 90 | 香港 | 任意 | 任意 | TAX_FREE |
| 70 | 欧盟 | 普通商品 | 任意 | EU_VAT |
| 60 | 美国 | 实物商品 | 任意 | US_SALES_TAX |

### B6 落地结构

只画真正需要的层，不要求为每种职责都创建一个类型。

```text
Context
  -> Policy（仅在存在独立业务决策时）
  -> Resolver / Decision Table
  -> Strategy
  -> Pipeline（仅在需要叠加时）
  -> Result
```

示例：

```text
TaxContext
TaxEligibilityPolicy
TaxModelResolver
TaxStrategy
TaxRateConfig
```

代码只给关键接口与分发点，标注「示意，按需调整」：

```go
type TaxStrategy interface {
    Calculate(ctx TaxContext) (Tax, error)
}
```

## C. 验证与边界

### C1 扩展性验证（最终目的）

明确回答：新增一个维度取值、新增一个业务类型、新增一条组合限制，分别要改哪些地方；改动是否局部化、能否独立测试。

```text
- 新增一个地区：决策表加一行 + 配置矩阵加列，不动策略代码。
- 新增一种商品税类：改 ProductTaxCategory 枚举 + 决策表 / 配置。
- 新增一种税务算法：新增一个 TaxStrategy 实现 + 决策表加一行。
- 新增一条组合限制：在 TaxEligibilityPolicy 加一个判断，不影响算法。
```

若某项改动会牵动多个不相关位置，说明维度或决策点还没拆对，回到 B3 重做。

### C2 不推荐的设计

```text
不建议：
- 为税费的每个组合建一个策略类型（笛卡尔积策略）。
- 把「中国香港免税」做成策略。
- 把纯税率差异做成策略。

原因：
- 组合策略数量爆炸，新增一个维度取值要改几十处。
- 免税是「能不能」，不是「怎么算」。
- 税率只是值不同，公式没变。
```

### C3 待确认问题

列出需要业务确认的假设，不要凭空补齐规则。

```text
- 退款时按当前税率还是下单时的快照税率？（影响是否需要版本化配置）
- 企业主体在香港是否也免税？
```

## Final Summary Template

分析结束时用以下格式总结：

```text
本需求中：
- xxx 是事实维度；
- xxx 只是普通数据字段，不参与维度建模；
- xxx 需要拆成 xxx；
- xxx 组合后派生中间模型 xxx；
- xxx 是参数；
- xxx 是规则条件；
- xxx 是策略分发条件；
- xxx 是非正交关系，应该用 xxx 处理；
- 推荐使用 xxx 结构；
- 不应为 xxx 建策略；
- 待确认：xxx。
```

## 建模原则

Rule / Policy / Config / Strategy 的边界、维度建模规则统一维护在 `SKILL.md`，本文件不重复。
