# 分析报告输出格式

只有确认存在多个独立决策点或多维组合时，才按 A / B / C 三段输出；没有内容的章节直接省略。简单或局部问题只输出「结论」加最小结构建议，不要套用完整模板。

本文件只定义**报告骨架**；判据与案例见 `dimension-and-context.md`、`pattern-selection.md` 与 SKILL.md。

---

## 输出总原则（可读性）

1. **结论先行**：先写 A 段，读者只读 A 段也能拿到答案；B 段为结论提供推理依据。
2. **维度分析用「原始 → 问题 → 目标」三段式**，要让读者看到推理链，不要只丢一行表格结论。
3. **表格只用于天然是矩阵的信息**（维度取值、维度角色、非正交判定、决策表）；判断理由一律用文字。
4. **代码只给关键接口、分发点和结构体字段**，标注「示意，按需调整」；不要铺空实现。
5. **术语首次出现给一句定义**，之后不重复解释；名词细节指向对应 reference。
6. **不使用「改造前 / 改造后」**：统一用「原始字段 / 业务描述 → 目标维度与结构」。
7. **篇幅自适应**：简单场景只输出 A + 必要小节 + 最小结构，不凑空章节。

---

## A. 结论

### A1 一句话结论

1~3 句说清：核心建模问题是什么、维度应该怎么拆、最终用什么结构承载。

> 示例：该需求的核心问题是 `ProductType` 一个字段同时承载商品形态、销售模式、贸易模式三层含义，导致每个决策点都在解析同一个字段。应先拆成四个独立事实维度；税费决策点在它们之上派生 `TaxModel` 中间模型，用决策表选模型、策略算金额。

### A2 结论速览

用一张紧凑表把「问题 → 结论」一次列清：

| 问题 | 结论 |
|---|---|
| `ProductType` 语义混杂 | 拆成 ProductForm / SaleMode / TradeMode / FulfillmentMode |
| 税费受地区、税类、主体共同影响 | 派生 TaxModel，用决策表选择 |
| 中国香港 + 任意商品 | 免税，属规则而非策略 |
| 税率随地区 / 税类变化 | Config Matrix，不建策略 |

## B. 分析过程

### B1 业务与决策点

按 **SKILL.md Step 1** 的方法（时间轴 + 四句 + 三格硬约束）列出决策点，并说明粒度过粗的拆分。表格按流程时间轴排序。

### B2 事实维度识别

先筛选，再分析。只把影响决策和变化的字段列为事实维度；只被读取、透传或展示的字段（如歌词、开播时间）明确写出并排除。

| 维度 | 含义 | 可能取值 |
|---|---|---|
| 地区 | 交易发生地 | 大陆 / 香港 / 欧盟 / 美国 |
| 商品税类 | 税务口径下的商品分类 | 普通商品 / 图书 / 数字服务 |

被排除的普通数据字段：`orderId`、`createdAt`、`lyrics`。

### B3 维度健康度分析（核心）

对每个有问题的维度，按统一三段式写推理段，并按四类问题分小节（没有该类问题就省略）：

```text
原始：<业务描述或字段 / 枚举长什么样>
问题：<太粗 / 语义混杂 / 层级平铺 / 强耦合 / Context 过大>
目标：<拆成哪些事实维度 / 派生什么中间模型 / 建什么层级；每个维度的取值与来源>
```

四类问题、判断信号与示例见 `dimension-and-context.md`（拆细 / 强耦合派生中间模型 / 层级 / Context 拆分）。

### B4 维度角色

先说清核心判断：同一个维度在不同决策点可以扮演不同角色。按 **SKILL.md Step 4** 的角色表，逐个决策点判断该维度是 Context 字段、Config 索引、Rule 条件，还是策略分发条件。

| 决策点 | 维度 | 角色 | 说明 |
|---|---|---|---|
| 价格计算 | 会员等级 | Config | 查折扣率 |
| 优惠资格 | 会员等级 | Rule | 判断等级是否足够 |
| 权益发放 | 会员等级 | Strategy 分发 | 不同等级流程不同 |

**规则识别**：只列需要跨 Policy 复用、独立配置或独立编排的 Rule；Policy 内部的简单判断不逐条建类型，放置规则见 `pattern-selection.md` 第 8 节。

| 规则 | 条件 | 结果 | 放置位置 |
|---|---|---|---|
| 中国香港免税 | 地区 = 香港 | 走免税，不征税 | 收进 TaxEligibilityPolicy |

**参数识别**：列出哪些逻辑只是「值不同」。

| 参数 | 索引维度 | 示例值 | 建模方式 |
|---|---|---|---|
| 税率 | 地区 × 商品税类 | 大陆 / 普通商品 = 0.13 | Config Matrix |

**策略识别**：列出哪些逻辑是真正的「怎么做」。若 Strategy 含多个方法，检查：是否同一能力？是否同一变化原因？是否同一生命周期？是否所有实现都必须提供？

| 策略接口 | 分发依据 | 策略实现 | 原因 |
|---|---|---|---|
| TaxStrategy | TaxModel | EUVAT / USSalesTax / MainlandIncludedTax | 算法不同 |

### B5 非正交维度处理（核心）

先判定关系本质，再给处理方式，不要急着把组合做成策略。五类判定与处理见 `dimension-and-context.md` 第 5 节。

| 非正交关系 | 类型 | 推荐处理 |
|---|---|---|
| 海外 × 赠品 | 非法组合 | Rule |
| 地区 × 商品税类 → 税率 | 同公式不同参数 | Config Matrix |
| 基础税 + 地区附加税 + 商品特殊税 | 多因素叠加 | Pipeline |
| 地区 × 商品税类 × 主体 × 发票 → 算法 | 互斥算法 | Decision Table + Strategy |
| 地区 × 商品税类 × 主体 → 税务口径 | 稳定业务概念 | Intermediate Model + Resolver |

需要中间业务模型时，给出「是否需要 / 原因 / 建议模型」，并可附优先级的决策表。

### B6 落地结构

只画真正需要的层，不要求为每种职责都创建一个类型。

```text
Context
  -> Policy（仅在存在独立业务决策时）
  -> Resolver / Decision Table
  -> Strategy
  -> Pipeline（仅在需要叠加时）
  -> Result
```

代码只给关键接口与分发点，标注「示意，按需调整」。

## C. 验证与边界

### C1 扩展性验证（最终目的）

明确回答：新增一个维度取值、新增一个业务类型、新增一条组合限制，分别要改哪些地方；改动是否局部化、能否独立测试。

```text
- 新增一个地区：决策表加一行 + 配置矩阵加列，不动策略代码。
- 新增一种商品税类：改 ProductTaxCategory 枚举 + 决策表 / 配置。
- 新增一种税务算法：新增一个 TaxStrategy 实现 + 决策表加一行。
- 新增一条组合限制：在 TaxEligibilityPolicy 加一个判断，不影响算法。
```

若某项改动会牵动多个不相关位置，说明维度或决策点还没拆对，回到 B3 重做。

### C2 不推荐的设计

```text
不建议：为税费每个组合建一个策略类型；把「中国香港免税」做成策略；把纯税率差异做成策略。
原因：组合策略数量爆炸；免税是「能不能」不是「怎么算」；税率只是值不同，公式没变。
```

### C3 待确认问题

列出需要业务确认的假设，不要凭空补齐规则。

```text
- 退款时按当前税率还是下单时的快照税率？（影响是否需要版本化配置）
- 企业主体在香港是否也免税？
```

```text
本需求中：
- xxx 是事实维度；
- xxx 只是普通数据字段，不参与维度建模；
- xxx 需要拆成 xxx；
- xxx 组合后派生中间模型 xxx；
- xxx 是参数 / 规则条件 / 策略分发条件；
- xxx 是非正交关系，应该用 xxx 处理；
- 推荐使用 xxx 结构；不应为 xxx 建策略；
- 待确认：xxx。
```
