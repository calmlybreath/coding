# 复杂业务维度建模

## 目标与最终价值

围绕业务决策点分析变化，不直接围绕用户、地区、商品等业务名词套设计模式。

最终目的是**可扩展、可维护**：新增一个维度取值、新增一个业务类型、新增一条组合限制时，改动是局部的、可独立测试的，而不是牵一发动全身。维度建错，后面的设计模式都会变形。

```text
事实是什么            -> Context
值是多少              -> Config / Matrix
单个判断条件          -> Rule（职责）
同一决策点的规则      -> Policy
选哪个模型或实现      -> Decision Table / Resolver
怎么算、怎么执行      -> Strategy
多个步骤依次叠加      -> Pipeline
状态如何合法流转      -> State Machine
```

## 适用判断

先判断是复杂建模问题，还是一个实现内的局部差异。只有一个决策点、少量分支时，直接给最小实现建议，不展开完整维度矩阵。

同一份数据、同一条查询、同一调用方，只是取值口径或读法不同，默认合在一个实现里。不要因为接口"以后可能变胖"提前拆；等独立变化真实出现后再抽象。

## 输出形态约定

- 结论先行：先给结论，再给推理依据。
- 维度分析一律采用「原始 → 问题 → 目标」三段式。
- 不使用「改造前 / 改造后」对比——代码可能尚未存在，统一用「原始字段 / 业务描述 → 目标维度与结构」。
- 完整报告结构见 `references/output-format.md`；简单场景只输出结论摘要与最小结构。

## 分析流程

### Step 0：明确输入与假设

收集业务目标、原始字段、关键分支、配置、状态和外部依赖。信息不足时区分：

- 已知事实；
- 合理假设；
- 待确认问题。

不要凭空补齐业务规则。上游数据库或协议给的形状若与业务含义不符，在建模层翻译，不要求改上游。

### Step 1：识别业务决策点

不要凭空枚举决策点。先按业务自身的流程写出时间轴（不预设阶段，取自当前业务），再沿时间轴在每个时间点固定问四句：

```text
能不能？   ← 准入、资格、支持性判断     -> 通常落成 Rule / Policy
多少？     ← 金额、比例、数量、积分     -> 通常落成 Config / Matrix / Pipeline
哪个？     ← 选模型、选实现、选路线     -> 通常落成 Resolver / Decision Table
怎么变？   ← 状态流转、阶段推进         -> 通常落成 State Machine
```

**硬约束**：每个决策点必须填满三格（决策问题｜输入事实｜决策输出），缺一格即视为分析未完成。整张表按流程时间轴排序，第一列标出所在时间点。

| 流程时间点 | 决策问题 | 输入事实 | 决策输出 |
|---|---|---|---|
| 下单 | 优惠是否可用？ | 会员等级、地区、活动类型 | allow / deny + 原因 |
| 计价 | 税费怎么算？ | 地区、商品税类、主体类型、金额 | 金额 + 命中的税务模型 |
| 支付 | 支付方式是否可用？ | 渠道、支付方式 | allow / deny + 原因 |
| 履约 | 订单状态如何流转？ | 当前状态、事件 | 新状态 |

三格填写要求：

- **决策问题**：动词句式的明确问题（「是否可用」「怎么算」「选哪个」「怎么流转」）。
- **输入事实**：参与该决策的事实维度。
- **决策输出**：具体形态——allow/deny + 原因、金额、选中的模型 / 实现、新状态。

若一个决策点的「输入事实」横跨不相关领域，或「决策输出」混了 allow/deny 与金额等不同类型，说明这个决策点太粗，应先拆成多个决策点再各填三格。

不要问"会员等级是不是策略"，而要问"会员等级在当前决策点中起什么作用"。

### Step 2：识别事实维度

先筛选，再分析。只把参与决策或变化分析的字段列为事实维度；只被读取、透传或展示的字段（如歌词、开播时间）是普通数据字段，明确排除，不进入后续分析。

对剩下的字段回答：

1. 哪些字段混合多个业务含义，需要拆细？
2. 哪些字段总是共同表达稳定业务语义，需要派生或封装中间模型？
3. 哪些字段存在父子层级？
4. 哪些字段只属于某个决策点？
5. 是否把数据库 Entity 当成了通用 Context？

如果筛选后只是一个决策点内的少量差异，回到「适用判断」给最小实现。

### Step 3：维度健康度分析（核心）

在判断维度应该建模为 Context、Rule、Policy、Config、Strategy 之前，必须先确认维度本身拆得是否正确：是否太粗、是否太散、强耦合维度是否被拆散、是否应该分层、Context 是否过大。

这是全流程唯一需要**跨决策点对账**的地方：把各决策点在 Step 1 列出的「输入事实」摆到一起，看同一个字段是否被不同决策点各取一条轴。这类问题在单个决策点内看不出来——枚举值越来越长、一个字段被多个不相关决策点解析，都是这里的信号。

对每个问题维度按「原始 → 问题 → 目标」写推理段，四类处理：

| 问题 | 处理 |
|---|---|
| 语义混杂或太粗 | 拆细成多个事实维度 |
| 强耦合、单独看无意义 | 保留原始事实，派生中间业务模型 |
| 层级被平铺 | 建立层级维度，上层分发流程、下层决定规则与参数 |
| Context 过大 | 按决策点拆 Context，只放该决策点需要的事实 |

同一个维度在不同决策点可以扮演不同角色；不同决策点用不同 Context。Context 是决策点的事实快照，不是数据库 Entity。判断信号、反例与案例见 `references/dimension-and-context.md`。

### Step 4：维度角色与非正交处理（核心）

对每个「决策点 × 维度」分别判断角色：

| 作用 | 建模方式 |
|---|---|
| 描述当前事实 | Context |
| 查询比例、阈值、开关 | Config / Matrix |
| 判断条件 | Rule（职责） |
| 选择中间模型或实现 | Resolver / Decision Table |
| 算法、流程、外部依赖不同 | Strategy |
| 多个步骤可组合叠加 | Pipeline |
| 状态与事件决定合法迁移 | State Machine |

不要问"它属于哪个模式"，要问"它在这个决策点里起什么作用"。

Policy 不是字段或维度角色：识别完规则后，把同一决策点的简单 Rule 直接收进 Policy；只有需要跨 Policy 复用、配置或独立编排时，才为 Rule 创建独立类型。

再处理维度之间的非正交关系：

| 关系 | 推荐方式 |
|---|---|
| 非法或不支持组合 | Rule |
| 公式相同，仅参数不同 | Config Matrix |
| 多个因素分别贡献结果 | Pipeline |
| 多维共同选择互斥算法 | Decision Table + Strategy |
| 组合形成稳定业务概念 | Intermediate Model + Resolver |

非正交关系的判定信号、决策表与中间模型案例见 `references/dimension-and-context.md`；模式边界不清时读 `references/pattern-selection.md`。

### Step 5：设计落地结构

推荐编排：

```text
Context
  -> Policy（仅在存在独立业务决策时）
  -> Resolver / Decision Table
  -> Strategy
  -> Pipeline（仅在需要叠加时）
  -> Result
```

这套编排是复杂场景的可选结构，不要求每一层都创建类型。只有一个实现的接口、只调用一次的 Resolver、只有一步的 Pipeline，应优先退回普通方法或局部分支。

接口围绕一个明确动词或决策点设计。避免 `UserStrategy`、`RegionStrategy` 等万能接口。

Strategy 不强制单方法。多个方法只有同时满足以下条件才放在同一接口：

- 表达同一业务能力；
- 因同一原因变化；
- 处于同一生命周期；
- 每个实现都必须提供。

Rule 描述判断条件，Policy 承载一个决策点的规则，Strategy 执行算法或流程。简单 Rule 直接写进 Policy；需要跨 Policy 复用、配置或独立编排时才抽成 Rule 类型。Strategy 内只保留依赖实现细节、与实现共同变化的不变量。

如果新增一个业务类型必须同时提供 Buy、Price、Inventory、Fulfillment 等多个独立决策点的能力，不要合并成万能 Strategy，也不要分散注册；使用 `ProductTypeModule` / `ProductStrategyFactory` 统一提供这些小接口，并通过构造校验和枚举覆盖测试检查完整性。

需要 Go 结构时读取 `references/go-implementation.md`。

### Step 6：扩展性验证与自检

逐项回答：

- 新增一个维度取值需要修改哪些位置？
- 新增一个业务类型需要修改哪些位置？
- 新增一条组合限制需要修改哪些位置？
- 以上改动是否局部化、能否独立测试？

如果某项改动会牵动多个不相关位置，说明维度或决策点还没拆对，回到 Step 3 重做。

同时检查是否拆过头：单实现接口、一条判断一个 Rule、把同一份数据和查询拆进多个实现。

## 自检清单

- 场景是否值得展开完整建模？（先判断，不套模板）
- 每个决策点是否填满三格？有没有输出类型混杂却未拆分的？
- 是否把普通数据字段当成了维度？
- 维度是否都拆得正确：太粗 / 太散 / 层级 / Context？
- 非正交关系的本质是否判断清楚？处理方式是否对应？
- 新增一个维度取值、业务类型、组合限制，改动是否局部化、能否独立测试？
- 是否拆过头：单实现接口、一条判断一个 Rule、同一份数据拆进多个实现？
- 是否给出最小、可测试的结构，并列出了待确认问题？
